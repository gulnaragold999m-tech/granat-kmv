# Анимация на сайте: движение со смыслом

Навык нужен, чтобы движение **работало на задачу страницы**, а не
на самолюбие исполнителя. Проверка одна: убрать анимацию — стало хуже
понятно? Нет — анимация лишняя.

Собран 18.08.2026. Опорные источники проверены по GitHub в тот же день:
официальный `greensock/gsap-skills` (восемь навыков по GSAP) и
`LottieFiles/motion-design-skill` (принципы моушна, MIT). Оттуда взяты
**принципы и приёмы**; всё, что касается React, Vue и сборщиков,
не взято — у нас их нет и не будет.

## Три вопроса до первой строчки кода

1. **Что анимация объясняет?** Появилось новое, ушло старое, элемент
   переехал, система думает, действие принято. Всё остальное — украшение.
2. **Сколько раз человек это увидит?** Один раз за визит — можно
   выразительно. Каждый раз при прокрутке — почти незаметно или никак.
3. **Как это будет на телефоне за 8 000 ₽?** Наша аудитория —
   КМВ и регионы, флагманов там меньшинство. Анимация, красивая
   на десктопе разработчика, там превращается в рывки.

## Бюджет движения

- **Не больше двух-трёх движущихся вещей одновременно** в поле зрения.
  Иначе взгляд не знает, за чем следить, и не следит ни за чем.
- **Первый экран до полной загрузки не анимируем.** Заголовок, который
  выезжает, — это заголовок, которого сначала нет. Поисковая метрика
  LCP считает именно первое появление главного элемента.
- **Никаких бесконечных анимаций рядом с текстом.** Мигающая точка
  в углу — ладно. Пульсирующая кнопка возле абзаца — читать невозможно,
  и на телефоне это ещё и батарея.
- **Место под элемент резервируется заранее.** Появление не должно
  сдвигать соседей: это CLS, и Яндекс с Google считают его прямо.

## Тайминги и кривые

Таблица — рабочая, не теоретическая. Дробить мельче нет смысла: разницу
в 30 мс никто не замечает, а разнобой в проекте заметен сразу.

| Что | Длительность | Кривая |
|---|---|---|
| Наведение, нажатие, фокус | 120–180 мс | `ease-out` |
| Микроответ формы (галочка, подсветка поля) | 150–250 мс | `ease-out` |
| Появление блока при прокрутке | 250–400 мс | `cubic-bezier(0.16, 1, 0.3, 1)` |
| Раскрытие меню, аккордеона | 250–350 мс | `ease-out` на вход, `ease-in` на уход |
| Крупная сцена первого экрана | до 800 мс | своя, один раз за визит |

Правила, которые за этим стоят:

- **Появление — `ease-out`, исчезновение — `ease-in`.** Входящее должно
  быстро показаться и мягко замереть; уходящее — наоборот. `linear`
  подходит только для бесконечного вращения загрузчика.
- **Уход быстрее прихода**, примерно вдвое. Ждать, пока закроется окно,
  раздражает сильнее, чем ждать, пока откроется.
- **Дольше 800 мс — это уже не анимация, а задержка.** Человек считает
  сайт медленным, хотя грузится он мгновенно.
- Кривые задаются в теме Tailwind один раз и дальше берутся классом.
  Новые заводить только с причиной.

## Двигать можно только `transform` и `opacity`

Это не стилистическое предпочтение, а устройство браузера. `transform`
и `opacity` считает видеокарта, отдельно от разметки. Всё остальное
заставляет браузер пересчитывать положение элементов на каждом кадре —
на телефоне это видно как рывки.

| Хочется | Делаем |
|---|---|
| `left`, `top` | `transform: translate()` |
| `width`, `height` | `transform: scale()` (следить за искажением текста) |
| `margin`, `padding` | переносим на обёртку или `translate` |
| `box-shadow` при наведении | псевдоэлемент с тенью и `opacity` |
| `background-position` | `transform` у слоя внутри |

`will-change` ставится точечно и заранее снимается: постоянный
`will-change` на десятке элементов съедает память и делает хуже.

## `prefers-reduced-motion` — обязательно, не «по возможности»

У части людей движение вызывает тошноту и головокружение; они включают
в системе «уменьшить движение». Сайт обязан это уважать — и это же
требование доступности из правил проекта.

```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: .01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: .01ms !important;
    scroll-behavior: auto !important;
  }
}
```

**Добавили анимацию — проверьте, что она попадает под глушение.**
Блок ставится один раз в `zhivoj-sajt/static/css/input.css` и накрывает
весь сайт.
Скрипт проверки ищет файлы, где `@keyframes` есть, а блока нет.

Отдельно: в JS то же самое читается через
`matchMedia('(prefers-reduced-motion: reduce)')` — иначе скриптовые
анимации проедут мимо настройки.

## Чем анимировать

**Порядок выбора: CSS → маленький собственный JS → GSAP → Lottie.**
Каждый следующий шаг дороже предыдущего по весу и по поддержке.

- **CSS закрывает процентов девяносто.** Наведение, фокус, появление,
  раскрытие, бесконечный загрузчик — всё это `transition` и
  `@keyframes`, без единого килобайта библиотеки.
- **Появление при прокрутке** — `IntersectionObserver` в десять строк.
  Библиотека для этого не нужна.
- **GSAP** — когда нужен таймлайн: пять элементов в заданном порядке,
  прокрутка, привязанная к сцене, пиннинг, обратное проигрывание.
  Подробно, включая подключение без сборщика, —
  `references/gsap-bez-sborshchika.md`.
- **Lottie** — когда нужна нарисованная сцена: персонаж, сложная
  иллюстрация в движении. Это самый тяжёлый вариант, и почти всегда
  вместо него хватает SVG с CSS — `references/lottie-i-svg.md`.

## Проверка

```
node .claude/skills/animacii-veb/scripts/proverka-dvizheniya.mjs zhivoj-sajt
```

Скрипт находит: анимацию свойств, которые нельзя анимировать;
длительности дольше 800 мс; файлы с `@keyframes` без глушения по
`prefers-reduced-motion`; бесконечные анимации; `will-change`, который
никто не снимает.

**Чего скрипт не проверяет:** уместность и красоту. Тормозит ли
на самом деле — тоже: это смотрится на живом телефоне, а не в коде.
